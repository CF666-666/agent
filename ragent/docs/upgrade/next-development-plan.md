# 工业 Ragent 后续开发方案

> 本文档用于沉淀工业 Ragent 后续开发顺序、技术目标、验收标准和简历口径。
> 目标不是继续横向堆叠 RAG 功能，而是围绕“可恢复 ETL + 多模态证据 + 工业关系检索 + 可复现评测”把现有升级做深。

**文档状态**：规划中
**基线日期**：2026-08-03
**适用项目**：`ragent/`
**主要目标岗位**：Java 后端校招；兼顾 AI/RAG 算法面试

---

## 1. 总体主线

项目后续开发统一围绕以下技术叙事展开：

```text
普通文本 RAG
    → 多模态文档解析与图像证据
    → 工业超边关系检索
    → 可恢复、可观测的知识入库闭环
    → 通道级 A/B 与质量回归
```

每个新增功能都必须回答两个问题：

1. 它解决了工业文档系统中的什么具体问题？
2. 它能否通过代码、测试或评测数据证明带来了增量收益？

不再优先开发与原版项目高度重合的功能，例如泛化的查询重写、意图树、会话摘要或新的模型供应商接入，除非它们直接服务于上述主线。

## 2. 当前能力与事实边界

### 2.1 已经具备的升级能力

- `IngestionNode` 可扩展入库节点，当前枚举包含 7 类节点：`Fetcher`、`Parser`、`Enhancer`、`Enricher`、`Chunker`、`Indexer`、`MultimodalParse`。
- `ConditionEvaluator` 支持 SpEL 字符串条件和 JSON `all/any/not/field` 规则。
- `IngestionEngine` 已具备路径环检测、节点执行日志和链式执行能力。
- 入库任务通过流水线、流水线节点、任务、任务节点 4 类持久化对象支撑前端管理和节点日志。
- 已实现 PDFBox、Tesseract OCR、Qwen-VL 多模态解析，以及图像独立 Milvus 集合和 `ImageSearchChannel`。
- 已实现工业 N 元超边、LLM Few-shot 抽取、正则降级、实体到超边倒排索引、读写锁和 `HyperGraphSearchChannel`。
- 已实现意图、向量、图像、超图四路检索，以及去重、多源归一化加权、Rerank 和 SSE `references`。
- 已具备检索 Hit Rate/MRR Runner 和 RAGAS 生成质量评测脚本。

### 2.2 当前不能过度描述的能力

- 当前 ETL 是以单个 `nextNodeId` 为主的链式执行，条件不满足时会跳过节点，但还不是真正的多出口 DAG 路由。
- 当前超图核心是实体精确匹配、倒排索引和命中数排序，尚未形成完整的多跳图搜索算法。
- 当前图像检索主要是“Qwen-VL 生成图像语义描述文本，再对描述文本向量化”，不能直接表述为原始图像向量检索。
- 当前没有实际的 BM25/Elasticsearch 检索通道，`KEYWORD_ES` 主要是预留类型。
- 当前评测报告尚未完成图像通道、超图通道的完整消融 A/B，也没有足够的多轮指代和多跳样本。

### 2.3 当前评测事实

现有报告记录：

- FAQ 精确评测 48 条：Hit Rate@1/3/5 均为 100%，MRR 为 1.0；
- 口语化评测 19 条：查询重写开启时 Hit Rate@1 为 94.74%，关闭时为 100%；
- RAGAS：Faithfulness 约 0.91，Context Precision 约 0.86，Context Recall 约 0.92。

FAQ 原文评测难度较低，不能单独作为“检索能力提升”的证据。后续简历数字必须来自可复现的评测报告，禁止直接使用没有数据文件、脚本或 A/B 记录支撑的数字。

## 3. 推荐开发顺序

```text
P0 真实基线与评测开关
        ↓
P1 ETL 分支路由、重试、幂等、续跑
        ↓
P1 HyperEdgeExtractNode 接入入库链路
        ↓
P2 实体归一化与有限多跳检索
        ↓
P2 通道级 A/B、延迟与成本回归
        ↓
P3 文档整理、演示闭环和简历校准
```

优先级说明：

- **P0**：没有基线就无法证明后续功能有效；
- **P1**：ETL 是 Java 后端最有辨识度的工程主线，同时是多模态和超边动态入库的基础；
- **P2**：把超图从“能检索”推进到“关系表达更可靠”，并用数据证明收益；
- **P3**：只在核心功能和指标稳定后做包装，避免文档描述领先于代码事实。

## 4. Phase 0：真实基线与评测基础

### 4.1 目标

建立固定的原版文本 RAG 基线，能够分别测量图像、超图和融合处理器的边际收益。

### 4.2 主要任务

1. 为问答入口增加评测专用通道开关：
   - `enableRewrite`
   - `enableImage`
   - `enableHyperGraph`
   - 必要时增加 `enableFusion`
2. 扩展 `SearchContext`，让通道开关只影响当前请求，不污染全局配置。
3. 构建分层评测集，至少覆盖：
   - 普通工业事实；
   - 口语化、术语替换和错别字；
   - 多轮指代；
   - 图纸和扫描件问题；
   - 设备—工况—参数—故障关系问题。
4. 每条样本标注：
   - `golden_doc_ids`；
   - `golden_image_ids`；
   - `golden_hyperedge_ids` 或关系路径；
   - 场景、难度、是否需要多跳。
5. 让评测脚本输出总体指标和按场景拆分的指标。

### 4.3 验收标准

- 同一评测集可以稳定运行文本基线、文本+图像、文本+超图、全链路四种配置；
- 不再只通过答案片段字符串相似度判断命中；
- 评测报告能定位到具体样本、来源类型和命中的文档/图片/超边；
- 当前评测结果与 `ragent/docs/evaluation-report.md` 保持一致。

### 4.4 产出

- 评测集 JSONL；
- 通道开关和评测脚本；
- 基线报告；
- 评测数据说明文档。

## 5. Phase 1：ETL 编排引擎升级

### 5.1 目标

将当前“单链路节点执行”升级为“支持条件分支、失败处理和可恢复执行的文档处理图”，同时兼容已有 `nextNodeId` 配置。

### 5.2 推荐执行示例

```text
Fetcher
  → Parser
  → 文件类型/文本密度判断
      ├─ 电子 PDF → PDFBox
      └─ 扫描 PDF → Tesseract OCR
  → Chunker
  → HyperEdgeExtract
  → Indexer
```

### 5.3 技术任务

#### A. 显式边模型

当前 `NodeConfig.nextNodeId` 只能表达一条后继边。建议增加兼容式边模型：

```java
class NodeEdge {
    String edgeId;
    String fromNodeId;
    String toNodeId;
    JsonNode condition;
    int priority;
}
```

旧配置仍可由 `nextNodeId` 转换成默认边，新配置使用 `edges` 表达多个出口。

#### B. 图校验

新增独立的 `PipelineGraphValidator`，负责：

- 节点 ID 唯一性；
- 边引用存在性；
- 起始节点和终止节点检查；
- 路径环检测；
- 不可达节点检查；
- 条件边优先级冲突检查。

#### C. 条件路由

保留现有 SpEL 和 JSON 条件解析器，但把结果从“是否执行当前节点”升级为“选择下一条边”。建议规则：

1. 按边优先级从高到低判断；
2. 第一条满足条件的边作为后继；
3. 没有命中条件时使用默认边；
4. 多条同优先级边同时命中时记录配置错误并终止任务。

#### D. 任务状态和恢复

节点状态至少包含：

```text
PENDING → RUNNING → SUCCESS
                    ↘ SKIPPED
                    ↘ FAILED → RETRYING
```

建议增加：

- 最大重试次数；
- 节点级超时；
- 最后成功节点；
- 当前尝试次数；
- 节点开始/结束时间；
- 可恢复任务入口；
- 失败节点人工重跑入口。

#### E. 幂等与重复入库

为文档任务生成稳定幂等键，例如：

```text
documentHash + pipelineId + pipelineVersion
```

同一文档、同一流水线版本重复执行时，应能够识别已有任务或安全覆盖对应索引，而不是产生重复 Chunk。

### 5.4 验收指标

- 分支路由用例通过率 100%；
- 环检测和不可达节点检测覆盖正常、异常、空图等边界；
- 模拟节点失败后可按策略重试并恢复；
- 同一文档重复提交不产生重复索引；
- 能按节点查看耗时、状态、错误和截断后的输出；
- 记录吞吐量、单节点 P95 耗时和任务成功率。

### 5.5 简历映射

完成后可将第一条从“可配置 Pipeline”升级为：

> 独立实现支持条件分支、节点重试、幂等和失败续跑的文档入库编排引擎……

在此之前不要写“DAG 分支路由”“断点续跑”或“任务幂等”。

## 6. Phase 2：超边接入文档入库链路

### 6.1 目标

让超边抽取不再依赖离线 JSONL 和启动时加载，而是成为文档入库过程中的正式节点。

### 6.2 主要任务

1. 新增 `HyperEdgeExtractNode`，从结构化文档或 Chunk 中抽取超边；
2. 保存 `sourceDocument`、`sourceChunkId`、页码/段落等证据位置；
3. 为超边增加文档版本和状态；
4. 新文档成功入库后增量更新倒排索引；
5. 文档删除、重新入库或版本切换时清理旧超边；
6. LLM 抽取失败时保留任务失败原因，不影响其他文档任务的故障定位。

### 6.3 推荐最小数据模型

先采用一张超边主表，扩展实体使用 JSONB，避免过早设计复杂图数据库：

```text
hyperedge
├── edge_id
├── equipment
├── condition
├── parameter
├── fault
├── sop_doc
├── extended_entities(jsonb)
├── source_document
├── source_chunk_id
└── document_version
```

应用启动时从数据库构建内存倒排索引，入库任务成功后支持增量更新。

### 6.4 验收标准

- 上传一份工业文档即可自动完成 Chunk、向量和超边入库；
- 超边能够追溯到原始文档和 Chunk；
- 重新入库不会残留旧版本超边；
- 删除文档后对应超边不再参与检索；
- 离线 JSONL 仍可作为 Demo 数据导入方式，但不再是唯一数据来源。

### 6.5 简历映射

完成后第三条可以强调：

> 将超边抽取接入文档 ETL，实现超边与文档版本、Chunk 和来源证据的同步管理。

这比单独描述一个内存倒排索引更能体现完整后端系统能力。

## 7. Phase 3：实体归一化与有限多跳检索

### 7.1 目标

将当前“实体精确匹配 + 命中数排序”推进为可解释、可控的工业关系检索。

### 7.2 推荐顺序

#### A. 实体归一化

- 设备编号和设备别名统一；
- 中英文、简称、俗称映射；
- 常见错别字和口语表达归一化；
- 维护可配置的工业术语映射表；
- 对归一化后的实体做短 TTL 缓存。

#### B. 匹配打分

将当前简单命中数扩展为组合分数：

```text
score = 实体命中率
      + 实体类型权重
      + 设备编号精确匹配奖励
      + 来源质量权重
      - 版本过期惩罚
```

#### C. 有限多跳

只做有边界的 1～2 跳搜索，不追求无限图遍历：

- 限制最大跳数；
- 限制候选超边数量；
- 记录每一跳的来源；
- 对循环路径去重；
- 无可信路径时回退到单边结果。

#### D. 结构化路径输出

返回：

- 节点列表；
- 超边列表；
- 每一步的匹配实体；
- 来源文档和 Chunk；
- 路径分数；
- 是否为单跳或多跳。

### 7.3 验收指标

- 实体归一化准确率；
- 超边 Recall@K；
- 多跳问题路径命中率；
- 路径来源准确率；
- LLM 实体抽取失败率；
- 超图通道平均延迟和 Token 成本。

### 7.4 简历边界

在有限多跳和来源校验完成前，建议使用“超边关系检索”或“结构化关系检索”，不要直接表述为“复杂超图推理引擎”。

## 8. Phase 4：通道级 A/B 与质量回归

### 8.1 实验配置

固定模型、数据集、Top-K 和 Prompt，仅改变通道：

| 配置 | 通道 |
|---|---|
| A | 意图 + 向量文本基线 |
| B | A + 图像 |
| C | A + 超图 |
| D | A + 图像 + 超图 + 多源融合 |

### 8.2 指标集合

#### 检索效果

- Hit Rate@1/3/5；
- MRR 或 NDCG；
- 文档 Recall@K；
- 图像 Recall@K；
- 超边/关系路径 Recall@K；
- 引用准确率。

#### 生成质量

- Faithfulness；
- Context Precision；
- Context Recall；
- Answer Relevancy。

#### 工程指标

- 检索 P50/P95 延迟；
- 首字响应延迟；
- 端到端 P95 延迟；
- Prompt/Completion Token；
- 单请求估算成本。

#### 入库指标

- 文档处理成功率；
- 节点失败率；
- 自动重试成功率；
- 重复入库率；
- 文档吞吐量；
- 单节点 P95 耗时。

### 8.3 评测原则

- 不使用只包含 FAQ 原文的单一简单集作为唯一证据；
- 结果必须按场景拆分；
- 同时报告平均值和困难样本表现；
- 每次代码改动保留 JSON 原始结果；
- 只有完成 A/B 且样本量足够后，才将提升百分比写入简历。

### 8.4 推荐简历表达

尚未获得真实提升数字时：

> 构建覆盖文本、图纸和关系路径的分层评测集，支持通道级 A/B，对检索命中、答案忠诚度、延迟和 Token 成本进行回归分析。

获得可靠数字后：

> 通过通道级 A/B 验证超图检索使多跳问题关系路径命中率提升 X%，图像问题 Recall@5 提升 Y%，并将 Faithfulness 和 P95 延迟纳入回归门禁。

## 9. 不建议当前优先开发的方向

### 9.1 BM25/Elasticsearch

除非评测证明工业编号、型号和标准号的精确匹配存在明显缺口，否则不优先引入新的搜索基础设施。当前项目已有向量、意图、图像和超图四类通道，继续增加通道会先增加延迟和融合复杂度。

### 9.2 视频检索

视频抽帧、关键帧索引和视频证据展示开发成本较高，且当前项目核心故事已经由图纸和超边关系支撑。除非有明确的工业维修视频数据集，否则暂缓。

### 9.3 继续堆模型供应商

模型路由和故障降级已经是原项目较成熟的能力，新增供应商对简历差异化有限，不应压过 ETL 和关系检索主线。

### 9.4 直接宣传“多跳推理”

在有限多跳、路径去重、来源校验和评测完成前，使用“超边关系检索”更准确。

## 10. 每个开发闭环的固定流程

每次只推进一个可验收闭环：

1. 明确问题、范围、接口和文件清单；
2. 先补测试或评测样本；
3. 实现最小功能；
4. 编译和运行单元/集成测试；
5. 更新对应文档和评测结果；
6. 记录当前实现边界和已知问题；
7. 再开始下一个闭环。

代码任务继续遵守仓库根目录 `DEVELOPMENT.md` 的协作规范，尤其是先方案确认、再编码、必须编译自测和等待验收。
