# Ragent 校招简历证据化开发计划

> 状态：执行中；R1 已完成，下一阶段为 R2
>
> 确认日期：2026-08-12
>
> 目标岗位：Java 后端校招
>
> 文档定位：本轮后续开发的权威入口；既有 `dev-roadmap.md` 与 `next-development-plan.md` 保留历史背景和已完成阶段记录。

## 1. 目标与主线

本轮开发不再横向堆叠检索通道，而是围绕一条可验证的项目主线收口：

> 可恢复的知识入库 → PDF 智能解析 → 多模态证据检索 → 工业关系检索 → 分层评测 → 可视化编排

所有功能最终都要形成以下证据链：

1. 代码和自动化测试证明能力已经实现；
2. 固定数据集、配置指纹和原始报告证明指标可复现；
3. 严格 A/B 只改变一个实验变量；
4. 简历描述与代码、数据集规模和报告完全一致；
5. 每个闭环独立测试、提交并推送，不将多个开发点混在一个提交中。

## 2. 已核验的真实基线

### 2.1 已实现能力

| 能力 | 当前事实 |
|---|---|
| ETL 节点 | 已实现 Fetcher、Parser、Enhancer、Enricher、Chunker、Indexer、HyperEdgeExtract、MultimodalParse 共 8 类节点 |
| ETL 图模型 | 后端已有显式 `edges`、条件优先级、默认边、环检测、可达性校验，并兼容旧 `nextNodeId` |
| 任务可靠性 | 已有任务幂等、检查点恢复、租约认领、节点状态和日志持久化 |
| 多模态解析 | PDFBox、Tess4J、Qwen-VL 解析器均已存在 |
| 图像检索 | 图像描述可独立向量化，并通过图像通道返回原始图像引用 |
| 超图 | 已有 N 元超边、持久化、实体倒排索引、读写锁、1～2 跳路径和来源证据 |
| 前端数据通道 | 已有流水线、任务、节点日志等管理页面，但流水线编辑仍为表单/JSON，不是画布式编排 |

### 2.2 尚未闭环或不能过度描述的能力

| 项目 | 当前限制 | 简历边界 |
|---|---|---|
| 扫描 PDF 自动处理 | PDF 默认按电子 PDF 解析；自动识别扫描页并降级 OCR 仍是 TODO | 完成按页自动路由前，不写“自动识别扫描件并 OCR” |
| 可视化编排 | 前端只能逐字段填写节点或编辑 JSON | 画布端到端验收前，只能写“配置化编排” |
| 超图效果 | 官方全链路报告中的关系场景 Hit@1 为 48% | 优化并经冻结集验收前，不强调“高质量推理”或写提升比例 |
| 口语鲁棒性 | 现有样本主要给完整问题添加口语前缀，未覆盖错词、省略和多轮指代 | 不能用现有 96% 证明多轮指代能力 |
| 图像规模 | 当前图像场景为 25 条问题、12 张素材 | 不能写“100 条图纸评测集” |
| 主评测规模 | 当前四场景各 25 条，共 100 条 | 不能写“200/240/250 条评测集” |
| RAGAS | 当前只有 12 条有效样本 | 不能写“RAGAS 60 条” |

| 问题 | 决策 | 优先级 | 原因 |

| GitHub Star/仓库按钮 | 删除 | P0 清理项 | 用户已明确要求；无简历技术收益，随首个闭环完成 |

| 视频检索、BM25、新模型供应商 | 不做 | 非目标 | 与本轮简历证据链关系弱，会分散开发投入 |

## 4. 最终评测设计

### 4.1 单轮主评测集：240 条

| 场景 | 样本数 | 主要覆盖 |
|---|---:|---|
| 事实检索 | 50 | 设备知识、参数、规程和故障事实 |
| 单轮噪声 | 40 | 简称、同音/形近错词、单位变体、语序混乱和信息省略 |
| 工业图像 | 100 | 设备识别、部件定位、参数读取、故障现象 |
| 关系检索 | 50 | 实体别名、相似实体干扰、单跳和 1～2 跳关系 |
| 合计 | 240 | 四场景分层主集 |

主报告必须同时给出：

- 微平均：按全部 240 条计算；
- 宏平均：四个场景等权，避免 100 条图像样本主导结论；
- 各场景独立指标和 95% 置信区间；
- Hit@1/3/5、MRR、P50/P95、超时率、空引用率；
- expected channel 命中率、golden source 命中率；
- 数据集 SHA-256、运行标签、模型版本、通道开关、预算和预热策略。

### 4.2 多轮指代集：20 组

多轮集独立于单轮主集，每组 2～3 轮，覆盖：

- “它”“这个参数”“刚才那个故障”等指代；
- 设备或故障信息省略；
- 同一会话内的话题延续与话题切换；
- 无法安全补全时的澄清行为。

对查询重写开启/关闭进行严格 A/B，报告 Hit@1、MRR、改写成功率、错误改写率、P95 和 Token 成本。

### 4.3 工业图像集：40 张素材、100 条问题

素材分层：

- 工程图、P&ID、原理图：20 张；
- 扫描手册页或设备铭牌：10 张；
- 工业现场照片：10 张。

约束：

- 每张图 2～3 条非同义问题；
- 每条素材保存来源 URL、授权、文件哈希和类别；
- 无法确认授权的素材不进入公开数据集；
- 按图片而非问题拆分调优集与冻结集，同一图片不得跨集合；
- 问题不能直接从入库使用的 Qwen-VL 描述模板化反推；
- 总称使用“工业图像评测集”，工程图子集才称“图纸评测”。

### 4.4 RAGAS：60 条

按检索证据类型分层，每层 15 条：

- 文本事实；
- 单轮噪声；
- 图像证据；
- 关系路径。

同时附加故障诊断、操作规程、维护保养、安全规范等业务标签。报告至少包含 Faithfulness、Context Precision、Context Recall、有效样本数、失败样本数和置信区间。

`answer_relevancy` 当前评分稳定性不足。在评估模型和重复运行稳定性验证完成前，只保留在内部报告，不进入简历。

### R1：PDF 按页智能解析与 OCR 降级

目标：电子 PDF、纯扫描 PDF 和图文混合 PDF 都能自动选择正确解析策略。

设计范围：

- 新增独立的 PDF 解析策略选择 seam，避免继续膨胀 Pipeline 节点；
- PDFBox 逐页提取文本并计算有效字符数或文本覆盖率；
- 文本充分页面保留 PDFBox 结果；
- 空白或低文本密度页面渲染为图片，交给 Tess4J；
- 按页码合并文本，保留页级来源；
- 支持 `AUTO`、强制 `PDFBOX`、强制 `OCR`；
- 记录 parser mode、OCR 页码、触发原因、页数和耗时；
- OCR 未就绪或失败时显式失败，不把空文本当作成功结果。

验收：

- 电子 PDF 不触发 OCR；
- 纯扫描多页 PDF 全部 OCR；
- 混合 PDF 只 OCR 需要降级的页面；
- 强制策略可覆盖自动判断；
- 页序、来源和任务失败状态正确；
- 单元测试、解析集成测试和真实入库端到端测试通过。

简历门槛：完成后可写“电子页/扫描页自动识别与按页 OCR 降级”。

闭环进度：

| 编号 | 内容 | 状态 | 验收证据 |
|---|---|---|---|
| R1-A | 页级解析领域模型与策略选择 seam | ✅ 完成 | `AUTO/PDFBOX/OCR`、电子页/扫描页/空白页/短文本/替换符与 mojibake 乱码决策及有序类型化结果共 11 项新增测试通过；阈值必须显式携带策略版本 |
| R1-B | PDFBox 逐页分析与视觉覆盖率 | ✅ 完成 | 按 PDF 内容解析 `.tmp` 文件；逐页提取文本/字符数；图像覆盖率按几何并集、CropBox 与裁剪路径计算，4 项集成测试通过 |
| R1-C | 页级渲染、Tess4J OCR 与失败传播 | ✅ 完成 | AUTO 仅渲染/OCR 目标页，强制模式无隐式回退；OCR 未就绪、异常或空文本均带页码使整文档失败；页图及时释放，5 项协调器测试通过 |
| R1-D | Pipeline、Chunk 页码来源与真实入库验收 | ✅ 完成 | 多模态节点按 MIME 将 PDF 接入页级解析器；类型化结果进入检查点和节点输出，页码/策略/原因贯穿 Chunk；OCR 异常阻止部分结果发布；无法保持页码映射的全文增强被显式拒绝；真实混合 PDF 分析、渲染、路由与分块链路通过，R1 聚合 28 项测试通过 |

### R2：超图关系检索质量

目标：修复“超图通道有结果，但正确超边和来源没有排到前面”的问题。

顺序：

1. 在 50 条关系数据上先运行旧实现，生成基线；
2. 对失败样本分类为实体漏抽取、别名未归一、超边缺失、排序错误、来源 ID 不一致和融合挤压；
3. 建立设备别名、编号、单位及常见错词归一化；
4. 校准实体类型权重、单边分数和 1～2 跳路径分数；
5. 统一 `hyperedge_id`、`source_document`、`source_chunk_id` 的评测映射；
6. 分别测超图通道原始结果和融合后的最终结果；
7. 只在冻结集上进行最终验收。

专属指标：

- 查询实体抽取准确率；
- Hyperedge Recall@1/3/5；
- 关系路径命中率；
- 来源准确率；
- 空路径率与错误扩展率；
- 通道延迟和 Token 成本。

目标门槛：

- 冻结集关系 Hit@1 ≥ 70%；
- Hyperedge Recall@5 ≥ 85%；
- 来源准确率 ≥ 90%。

目标值用于验收，不预写入简历；最终只使用实测结果。本阶段保留现有 1～2 跳，不扩展到三跳。

闭环进度：

| 编号 | 内容 | 状态 | 验收证据 |
|---|---|---|---|
| R2-A | 超图查询可用性：本地实体优先与预算受控 LLM 兜底 | ✅ 完成 | 从不可变索引快照匹配规范名与别名；高置信本地命中不调用 LLM，本地零命中且剩余预算充足时才兜底；短 ASCII 标识符使用词边界，两字中文故障词可识别；本地扫描和 1～2 跳遍历响应取消；`DEGRADED` 排除质量计分；Java 20 项、Python 5 项测试通过，独立复审无 P0/P1 |
| R2-B | 关系冻结集基线与失败分类 | ✅ 完成 | 固定 50 条、tuning/frozen 各 25 条且超边隔离；SSE 透传结构化证据，50/50 可计分，逐超边 Hit@1/5=74%/82%、Recall@5=77%、严格有序路径=30%、逐边来源=74%；无因果越界分类已归档，42 项离线测试与 3 项引用投影测试通过 |
| R2-C | 实体归一化与来源 ID 对齐 | ✅ 完成 | C1 统一 Unicode/大小写/空白/单位并补齐 4 个 tuning 简称；C2 对 6 类证据字段输出真实值及 available/unavailable/conflicting，禁止伪造 chunk/page。Java 31 项、Python 49 项及真实 SSE 探针通过 |
| R2-D | 类型权重、1～2 跳路径评分与冻结集 A/B | ⬜ 待开始 | 严格 A/B 达成阶段门槛或如实记录未达标结果 |

### R6：可视化编排画布

目标：真正以图形方式编辑并执行后端现有的显式 DAG，而不是给旧 `nextNodeId` 表单加流程图外观。

范围：

- 引入 React Flow；
- 左侧提供 8 类节点面板；
- 支持拖拽创建、移动、删除节点及拖拽连线；
- 节点侧栏编辑节点配置；
- 边侧栏编辑 SpEL/JSON 条件、优先级和默认边；
- 保存和加载完整 `nodes + edges`；
- 前端即时检查重复节点 ID、悬空边和多个默认出口；
- 后端继续负责环检测、可达性和最终配置校验；
- 保留 JSON 高级编辑模式；

任何未满足门槛的能力可以写为“设计/实现”，但不能使用未运行的规模、目标值或提升百分比。

复杂度表述统一为：

> 通过实体到超边的倒排索引，将单实体候选召回由全图扫描收敛为与命中超边数相关的 O(k) 访问。

不笼统宣称“整个关系检索复杂度为 O(k)”，因为查询仍包含实体抽取、归一化、路径扩展和排序。

## 7. 每个闭环的固定流程

1. 开发前依据本文确认该闭环的范围和非目标；
2. 先固定输入、验收样本和失败反例；
3. 通过稳定接口接入，避免在 Pipeline、检索、融合核心中堆叠类型分支；
4. 完成主流程、异常兜底、并发一致性和可观测字段；
5. 运行定向单元测试、必要的集成测试和端到端验收；
6. 更新本文进度、相关设计文档和测试证据；
7. 只暂存该闭环文件，提交信息包含闭环编号，例如 `feat(r1-a): add page-level PDF parse routing`；
8. 提交并推送成功后再进入下一闭环。
